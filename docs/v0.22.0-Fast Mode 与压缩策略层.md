# v0.22.0 — Fast Mode：只读轮走快模型 + 压缩策略层

> 日期：2026-09-02。插件 `0.21.1` → `0.22.0`。

Socrates 原来只有一个模型。所有轮次——「问我一个问题」「举两个例子」「给段代码」
和「把解答写进手册」——都打同一个基座，同一个价钱，同一个速度。

但这些轮次的性质差得很远。绝大多数气泡是**只读**的：模型顶多 `read_file` 翻一下
手册、`fetch` 取个网页，然后说话。只有写回类的轮次才真的要动磁盘。只读轮不需要
基座的深度，它需要的是**快**。

这一版做**动态路由**：侧栏顶栏一枚闪电开关，开着时按硬规则判定这一轮是不是只读，
是就走快模型，否则走基座。

**但快模型的窗口只有 131072（input + output 合计），基座是 1M 档。** 所以 Fast Mode
必须自带上下文压缩，而这份压缩**不能污染会话**——现有的 `compact_session()` 是就地
破坏性的，折一次 `session.compacted` 就永久为真，之后连基座轮次也再拿不到目录 /
邻域 / 书架。这就逼出了这一版真正的结构改动：**把「怎么压」和「压完写给谁」拆开**。

---

## 一、端点事实（本机实测，不是查来的）

| 项 | 结果 |
|---|---|
| 窗口 | **131072 = input + max_tokens 合计**，请求时硬拒，不是生成时截断 |
| 最大输出 | **16384**（16385 即 400） |
| 实际输入硬顶 | `131072 − max_tokens`；满档输出时 **114688** |
| 吞吐 | **249 tok/s**（1200 token / 4.83s） |
| 流式 / 工具 / 视觉 | 全部 ✅，含组合 |
| 推理字段 | **`delta.reasoning`**，不是 DeepSeek 的 `reasoning_content` |
| 推理档 | **`none` / `low` / `medium` / `xhigh`——没有 `high`**（传了当场 400） |
| `extra_body.thinking` | 收下但**完全不理会**（disabled 照样吐 49 个 reasoning token） |
| 中文 token 比 | **0.583 tok/字**（20K / 60K / 120K 三档一致） |

最后两行不是优化，是**正确性**：设置页的 Thinking 有「high」这一档，不映射成
`xhigh` 的话，每一个高档快轮都会当场 400。

## 二、五个拍板

| # | 决策 | 理由 |
|---|---|---|
| 1 | 快轮**写不了盘**，要写就自动升级到基座 | 路由再保守也会漏判；靠模型自己开口要 `edit_file` 是比任何关键词表都准的信号 |
| 2 | 快模型走**设置页三件套 + 独立 key 通道** | 跨主机保护：换主机没自带 key → 判成没配置。而 `check-key.mjs` 禁止 `api_key` 随请求体上行 |
| 3 | 只覆盖**主对话 `/v1/chat`** | 折叠块生成 / 后台深挖 / 诊断评语三处各有独立预算体系，这一版不动 |
| 4 | 压缩做成**策略层**，Fast 用非破坏副本 | 见开头。这是本版唯一的结构性改动 |
| 5 | 词表要**准**，不要宽 | 见 §4 的代价模型 |

### 决策 1 用绊线，不是摘工具

原设想是「把 `edit_file` 从工具表摘掉」，但摘掉就没有确定性触发信号了——模型只能
用散文说「我想改这里」，那是模糊判定；而且 `session.py` 有三行 system prompt 承诺
`edit_file` 存在，摘了工具就得同步裁剪提示。

改成**绊线**：快轮照常把三个工具都挂上，但 `_agent_loop` 在 **dispatch 之前**拦截。
效果完全一致（快轮物理上到不了 `handle_edit_file`），但触发是确定性的，
`schemas()` 和 system prompt 一个字都不用改。

判据不在 tutor 里另列一遍工具名，而是**借 `permissions.decide()`**——「哪些工具会
动磁盘」是那个模块的职责。两处分家的话，将来多一个写类工具就会出现「审批面板弹了、
但快模型已经把它执行完了」。

### 升级为什么不需要回滚

`session.messages` 是**供应商中立**的，而 `session.messages.append(reply)` 发生在
检测点**之后**。所以：

1. 检测到 → **不 append** 那条 assistant 消息。带 `tool_calls` 的消息必须有配对
   tool 结果，不 append 就没有这个配对义务，历史天然合法。
2. 重绑 `cfg` / `client`（`_create` 是闭包，读的就是这两个名字）
3. `yield {"type": "route", "to": "base"}` → 前端清空当前气泡重流
4. `continue` → 下一枪在基座上跑，**快模型已经读到的正文全部保留**

`ctx["read_ok"]` 也已经被快模型的成功读更新过，所以基座的 `edit_file` 直接过
`read_first_block` 硬闸，不用重读。代价只有浪费的那一枪。

## 三、压缩策略层

### 病灶

`compact_session()` 把「怎么压」和「压完写给谁」焊死了：

```python
session.messages = [*system, summary, *slimmed_last]
session.read_ok_paths = []
session.compacted = True          # 全仓无处置回 False
session.last_context_tokens = 0
```

`compacted=True` 之后每个 packet 都永久走精简路径，目录 / 邻域 / 书架再也不重喂。
**Fast Mode 折一次，基座轮次也永久降级。**

### 新结构

- `pen/compact.py` 拆成「纯变换」（`split_last_turn` / `fold_messages`）+「破坏性
  外壳」（`compact_session`）。**现有 12 条 `test_compact.py` 一条没改，全绿**，
  这就是重构的回归闸。
- 新增 `pen/compaction.py`：`Budget` / `CompactionPlan` / `Strategy` /
  `STRATEGIES` / `strategy_for`。形状照 `pen/agent/registry.py` 的 `TOOLS` 表。

```
基座 / 手动命令  到阈值折一次，折成固定形状，就地改会话   → RollingSummary
Fast Mode        按预算逐级降，压到够用为止，只给副本     → FastWindow
```

**策略只负责「算出该发什么」，一律返回 `CompactionPlan`，谁都不写回 session。**
`compact_session` 仍是唯一一处破坏性入口。

### `FastWindow` 的降级阶梯

严格照仓里既有的压缩哲学（`cap_selected_text` / `neighborhood` / `_thin_by_level`
全都这样）：**够用就原样返回，超了才降级，降完在文本里明说降了什么。**

```
0  预算够        原样返回，changed=False，零成本
1  stub-history  更早回合的工具结果换存根（正文丢了可以再 read）
2  slim-history  更早回合 user 包里的目录/邻域/书架换成一句引用
3  fold          整段折成滚动摘要（这一步才动最后一轮）
-  仍然超        fits=False，调用方退回基座
```

最后一轮**留到第 3 档才动**：那是模型这会儿正要用的材料，先扔它等于为了省窗口
把这一轮问废。第 4 步的兜底是诚实的：把上下文压成废墟去迁就窗口，还不如让基座跑。

### 估算器踩过的两个坑

`message_chars(msgs)/2` 偏低约 14%，方向也相反（它宁可**晚**折，估低无害；
这里估低就是 400）。所以新写了一个偏高的 `est_tokens`。中间踩到两次：

1. **断崖**。第一版写成「CJK 过半就整段用 1.5，否则整段用 3.0」。同一段上下文，
   多贴几个长 ASCII 路径就能把占比压到阈值以下，估值当场减半——实测同一个夹具在
   两个不同长度的临时目录下走到了不同的压缩档。改成**按字符加权相加**，没有断崖。
2. **拉丁系数太松**。对着真端点量了四个样本，发现这个插件的拉丁部分主要是
   **代码和标识符**（`target_net(next_state).max(1)[0].detach()`），token 密度远高于
   英文散文，按「常见 4 字/token」算会当场估低。收到 2.5，最坏一格 1.12x。

### 循环内的窗口闸

`_agent_loop` 每轮把整段 messages 重发，`max_tool_rounds` 默认 100，每次 `read_file`
最多加 5000 字符且**永不裁剪**。基座 1M 窗口从没暴露过这件事；快模型是请求时硬拒，
**没有这道闸，快轮会在对话中途吃 400**。

它和旁边那道 `metermod.over` 花销闸**不同源**：那道量的是「这一轮花了多少钱」，
默认 0（关着）；这道量的是「这一枪有多大」。两者不能互相替代。

## 四、路由表

**这才是「哪些气泡走快模型」的真正定义点。** 所有气泡——固定的、自定义的、
动态追问、深挖题——都走同一个 `/v1/chat`，区别只在 `chip` 和 `user_text`。

| chip | 路由 | 依据 |
|---|---|---|
| `socratic` 先别揭晓，问我一个问题 | **Fast** | 只问问题 |
| `explain_zero` 当我零基础，讲清楚再给两个例子 | **Fast** | 只讲解 |
| `examples` 只举例子 | **Fast** | 只举例 |
| `search` | — | `app.py` 短路，压根不进模型 |
| `writeback` 把刚才的解答写进手册原文 | **Base** | 天然写回 |
| `free`（含全部动态追问 / 深挖题 / 读者手打） | 看 `user_text` | 无写入意图 → Fast |
| `u.*` 且 `writeback` | **Base** | 三个预置模板全是这一类 |
| `u.*` 且非 writeback | 看读者自己写的 prompt | |
| `POST /v1/chat/approve` 后半轮 | **Base** | 必然执行 `edit_file`（结构性：`ApproveBody` 上没有 `fast` 字段） |

### 词表要准，不是要宽（决策 5）

第一版 `_WRITE_INTENT` 只列动词（`改写|替换|插入|改成…`）。拿 15 条真实只读提问
一量，**误判 3 条，而且三条全是 tradeoff 问句**：

> 为什么 dispatch 不直接替换成 match 语句，代价在哪？
> 如果把学习率改成 0.1 会怎样？
> what would happen if we replace the buffer with a queue?

这正是深挖题的形状，也正是 Fast Mode 最该服务的那一类。
（`pen/questions.py:_CHORE` 的注释里记着同一个坑：那一版拿「替换成」连坐，把正当的
tradeoff 题也杀了。同一个教训，这里又踩了一次。）

计划里原本写的是「宁可多抓」——**那个代价模型是反的**：

```
漏判 → 写入轮跑到快模型。绊线当场拦下、换基座重打，代价一枪（约 1 秒）。
误判 → 只读轮跑到基座。整个提速没了，而这是最常见的轮次。
```

两边不对称，且方向和直觉相反。所以改成**锚宾语**（动词 + 12 字内的手册类宾语，
或反过来的语序，或祈使句式），拿 34 条黄金集量到 0 误 0 漏。兜底交给绊线，
那是确定性信号，比任何词表都准。

`_CHORE` 仍是「杂务」的唯一定义点，`wants_write()` 直接调 `is_chore()` 当第二个
信号，不长出第二张同义表。

## 五、两个新 SSE 事件，名字都是新的

| 事件 | 意思 |
|---|---|
| `route` | 快轮半路换回基座。前端**清空当前气泡重流**，并插一条 note 说清楚 |
| `trimmed` | 这一枪发出去之前压了副本。**不叫 `compacted`** |

第二条的命名是有意的。`compacted` 这个名字 `app.py` 已经占了，意思是「会话真被折了」
（破坏性、不可逆，前端往日志里插一条永久提示）。快轮压的是副本，会话一个字没动——
共用一个事件名就是对读者说谎。所以 `trimmed` 只挂在顶栏那枚开关的悬停提示上。

`route` 那条**必须清空气泡**：不清的话快模型开口那半句会和基座接下来整段叠在一起，
读者看到的是两个人在说话。清了又不解释，看起来就是个 bug——所以必须插 note。

## 六、凭据

第二组托管凭据，落在同一个 `PEN_DIR/llm.json`（0600，原子写）：

```json
{
  "api_key": "sk-…",      "base_url": "https://api.deepseek.com",
  "fast_api_key": "ck-…", "fast_base_url": "https://…/v1"
}
```

- 新端点 `PUT` / `DELETE /v1/llm/fast-key`
- `merge_fast_llm()` **没有 `api_key` 参数**——钥匙只走托管槽，永不随请求体上行
- 两把钥匙走**同一条** `putChain`：同一个文件的两个槽，后端是读-改-写，
  并发 PUT 会让后写的拿旧内容覆盖
- `/v1/health` 的 `fast` 格复用 `LlmStatus` 类型（后端 `fast_public_status` 就是
  照它写的），只露 key 末 4 位
- 没配 fast key → `route_for` 返回 `("base", "no-fast-key")`。**开关照常能开，
  只是不生效**，点开时探一次 health 当场说破。不做成硬错误。

**关掉 Fast Mode 时请求体里连 `fast_base_url` / `fast_model` 都不发**——后端确实
只在 `body.fast` 为真时才读它们，发了也无害；但「关掉之后与上一版逐字节一致」
是这一版对老路的承诺，多两个键就不叫逐字节了。

## 七、有意不做

- **折叠块生成 / 后台深挖 / 诊断评语不接路由**（决策 3）。`propose_fold_md` 天然
  适合快模型且改动干净，但它产出的是要写进手册的正文，质量敏感；深挖的 `cfg` 在
  spawn 时就冻进 `ProbeJob` 且有独立的预算体系。留作下一版。
- **不给 `LLMConfig` 加可变全局**。sidecar 是多会话共享进程，同一台可能同时伺候
  两个 vault。fast 配置照 `limits` / `custom_chip` 的先例随请求上行。
- **`session.compacted` 的语义不动**。Fast 的压缩走副本，压根不碰这个位。
- **`persistableSettings` 不加「滤掉未知字段」**。它从没承诺过这件事，`apiKey`
  那条也一样——靠的是 `main.ts` 装载时那句 `delete`。断言一条代码没做的保证，
  只会诱导别人去加一段防空气的代码。
